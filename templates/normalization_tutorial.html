Урок по нормализации данных

Что такое нормализация?

Нормализация — это процесс организации данных для:

  • Устранения дублирования информации
  • Предотвращения противоречивых данных
  • Упрощения работы с базой данных
  • Ускорения выполнения запросов

Три основные нормальные формы:

  1. 1НФ (Первая нормальная форма):
    • Нет повторяющихся групп данных (каждая ячейка содержит одно значение)
    • Нет дублирующих строк
    • Пример: вместо "101,102" в одной ячейке - отдельные строки для каждого значения
  2. 2НФ (Вторая нормальная форма):
    • Должна выполняться 1НФ
    • Все данные в таблице зависят от всего первичного ключа (а не от его части)
    • Пример: информация о пользователе не должна храниться в таблице заказов
  3. 3НФ (Третья нормальная форма):
    • Должна выполняться 2НФ
    • Нет зависимостей между неключевыми полями (все данные зависят только от ключа)
    • Пример: почтовый индекс → город → область (лучше вынести в отдельную таблицу)

Пример нормализации

Исходная таблица (ненормализованная)

user_id username email order_id product quantity address
1 Бакс Банни bucks@carrot.com 101, 102 Морковь премиум, Салат 5, 3 Нора №7, Морковное поле

Проблемы:

  • Несколько заказов в одной строке (нарушение 1НФ)
  • Адрес дублируется для каждого заказа
  • При изменении адреса нужно обновлять все связанные записи

Приводим к 1НФ

Устраняем множественные значения:

user_id username email order_id product quantity address
1 Бакс Банни bucks@carrot.com 101 Морковь премиум 5 Нора №7, Морковное поле
1 Бакс Банни bucks@carrot.com 102 Салат 3 Нора №7, Морковное поле

Улучшения:

  • Каждая строка содержит один заказ
  • Нет повторяющихся групп

Приводим к 2НФ

Разделяем данные по сущностям:

Таблица Users (пользователи):

user_id username email address
1 Бакс Банни bucks@carrot.com Нора №7, Морковное поле

Таблица Orders (заказы):

order_id user_id product quantity
101 1 Морковь премиум 5
102 1 Салат 3

Улучшения:

  • Нет дублирования информации о пользователях
  • Заказы ссылаются на пользователей через user_id
  • Устранили связь "один-ко-многим" (1 пользователь → много заказов)

Приводим к 3НФ

Устраняем скрытые зависимости:

Проблема: адрес содержит две сущности (номер норы и тип поля), которые могут изменяться независимо. Если несколько пользователей живут на одном поле, при его переименовании нужно обновлять всех пользователей.

Таблица Users (3НФ):

user_id username email location_id
1 Бакс Банни bucks@carrot.com 7

Таблица Locations (местоположения):

location_id address field_type
7 Нора №7 Морковное поле

Улучшения:

  • Информация о местоположении хранится централизованно
  • Изменение типа поля требует обновления только одной записи
  • Устранили транзитивную зависимость (поле → местоположение → пользователь)

Практическое задание

Распределите поля по таблицам для 3НФ. Обратите внимание на:

  • Устранение связи "многие-ко-многим" (разделение сущностей)
  • Исключение транзитивных зависимостей
  • Правильное использование внешних ключей
